## 2. 任务 A（已执行）：补齐运维检查的定时单元

### 执行前背景

`pnpm operations:check` 已存在且可用，执行前 `deploy/vps/` 下缺少对应的 systemd 单元，检查只能人工触发。

### 关键前提：不要直接复制 `cipc-labequip-backup.service`

备份单元的两条配置**会让运维检查失效**：

1. `PrivateNetwork=true` —— 会把服务放进独立网络命名空间，其中的 `127.0.0.1` 不是宿主的 loopback，`operations-check.mjs:54` 的 `fetch(apiUrl)` 打不到宿主上监听 `127.0.0.1:4000` 的 API，`checks.api` 必然 `failed`。必须去掉。

2. `ReadOnlyPaths=/var/lib/cipc-labequip/data` —— **实测会让数据库检查误报**。`operations-check.mjs:29` 以 `readOnly: true` 打开 WAL 库，而 WAL 模式即使只读访问也需要在库文件同目录创建/映射 `-shm`。本地复现（干净关闭、无残留 `-wal`/`-shm`、目录置为不可写）：

   ```
   RESULT: FAILED -> ERR_SQLITE_ERROR attempt to write a readonly database
   ```

   该异常会被 `operations-check.mjs:32` 的 catch 吞掉，转成 `checks.database = { status: "failed", reason: "attempt to write a readonly database" }` —— 库是好的，监控却报故障。这是最坏的一类误报：值班的人会去查一个不存在的数据损坏。

   数据目录用 `ReadWritePaths`，与正在运行的 `cipc-labequip-api.service`（`ReadWritePaths=/var/lib/cipc-labequip`）保持一致。备份目录只需 `readdirSync` + `statfsSync`，`ReadOnlyPaths` 即可。

   > 生产上 API 常驻持有该库，`-shm` 已存在，失败与否取决于 SQLite 能否拿到只读 shm 映射，行为可能与本地不同。**部署后必须在宿主上实跑一次确认 `checks.database.status === "ok"`，不要凭配置推断。**

### 新增文件

`deploy/vps/cipc-labequip-operations.service`：

```ini
[Unit]
Description=CIPC LabEquip Hub operations check
After=cipc-labequip-api.service

[Service]
Type=oneshot
User=cipc-labequip
Group=cipc-labequip
WorkingDirectory=/opt/cipc-labequip/current
Environment=API_HEALTH_URL=http://127.0.0.1:4000/api/health
Environment=DATA_FILE=/var/lib/cipc-labequip/data/production.sqlite
Environment=BACKUP_DIR=/var/lib/cipc-labequip/backups
ExecStart=/usr/local/bin/node scripts/operations-check.mjs --max-backup-age-hours 36 --min-free-mb 1024
NoNewPrivileges=true
PrivateTmp=true
PrivateDevices=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/cipc-labequip/data
ReadOnlyPaths=/var/lib/cipc-labequip/backups
```

环境变量名取自 `scripts/operations-check.mjs:65`，逐一核对过：`API_HEALTH_URL`、`DATA_FILE`、`BACKUP_DIR`。可用参数：`--api`、`--data`、`--backup-dir`、`--max-backup-age-hours`、`--min-free-mb`。

基础单元不内置 `OnFailure=`。具体接收命令、凭据和载荷格式属于站点配置，通过 systemd drop-in 连接已有告警单元。

`deploy/vps/cipc-labequip-operations.timer`：

```ini
[Unit]
Description=Run CIPC LabEquip Hub operations check periodically

[Timer]
OnBootSec=5min
OnUnitActiveSec=15min
Unit=cipc-labequip-operations.service
AccuracySec=1min

[Install]
WantedBy=timers.target
```

不要加 `Persistent=true`。它用于日历定时器补跑错过的任务，而健康检查补跑一次历史时点没有意义 —— 只会在开机时打一串无用的告警。

仓库当前没有可直接复用的告警命令，因此部署说明记录站点级接入方式：

```bash
sudo systemctl edit cipc-labequip-operations.service
```

```ini
[Unit]
OnFailure=SITE_ALERT_UNIT.service
```

`operations-check.mjs` 在失败时返回非零状态，基础能力会把单元标为 `failed` 并保留完整 journal；实际消息送达由部署方配置并验证。

## 4. 任务 C（本批跳过）：`updateMeetingRoom` 兜底分支的 `NaN`

### 事实

`apps/api/lib/service.mjs:1097` 用的是原始 `input.capacity`：

```js
const conflict = database.prepare("... AND people > ?").get(roomId, new Date().toISOString(), Number(input.capacity));
```

只改 `active` 时 `input.capacity` 是 `undefined`，`Number(undefined)` → `NaN`，`people > NaN` 恒为假，于是错误详情报出 `conflictingReservations: 0` —— 一条声称「容量低于预约人数」却说冲突数为 0 的自相矛盾响应。事务内的检查使用校验后的 `next.capacity`，是对的。

### 该分支不可达（第 1 版这里论证方向写反了）

第 1 版说「预约刚好在两次检查之间结束」会触发。方向是反的。触发器定义在 `database.mjs:588`：

```sql
CREATE TRIGGER meeting_rooms_protect_reservation_capacity
BEFORE UPDATE OF capacity ON meeting_rooms
WHEN EXISTS (
  SELECT 1 FROM room_reservations
  WHERE meeting_room_id = OLD.id
    AND status IN ('approved', 'in_use')
    AND end_at > STRFTIME('%Y-%m-%dT%H:%M:%fZ', 'now')
    AND people > NEW.capacity
)
```

谓词与服务层检查完全相同，`NEW.capacity` 就是校验后的 `next.capacity`。触发器的 `now` 晚于服务层的 `now`，而 `now` 越晚，满足 `end_at > now` 的行只会更少 —— 候选集是服务层的子集。服务层查到 0 行，触发器不可能查到。加上 `BEGIN IMMEDIATE` 持写锁，其他写入无法插队。所以这是防御性死分支，也**无法写出能触发它的回归测试**。

### 未来改法

保留分支（万一将来有绕过服务层检查的新路径，它还能返回 409 中文提示而不是裸 500），但让它不可能报出 `NaN` 派生的假数据。把校验后的容量提到 `try` 外：

```js
let validatedCapacity;          // ← try 之前声明
try {
  return transaction(() => {
    ...
    validatedCapacity = next.capacity;   // ← 校验通过后赋值
    ...
  });
} catch (error) {
  ...
  if (String(error.message).includes("meeting_room_capacity_conflict")) {
    const conflict = database.prepare("...").get(roomId, new Date().toISOString(), validatedCapacity);
    ...
  }
}
```

不写测试，理由如上。改动值在于「若它真的响了，报出的数字是真的」。

同一 catch 里 `meeting_room_has_future_reservations` 那个分支没有这个问题，不要动。

## 5. 已撤回：`canCancelReservation`（第 1 版 P1）

第 1 版建议把 `apps/web/app.js:272` 的 `currentRole === "developer"` 改成 `currentUser?.role === "developer"`。**这个建议是错的，不要执行。**

`currentRole` 是开发者的模拟视图角色。开发者切到普通用户视图时，会议室管理、成员管理等高级入口一并隐藏；「取消他人预约」按钮隐藏与这套语义一致。只把取消按钮换成真实角色，会造成普通用户模拟视图里唯独残留一个开发者专属操作 —— 比现状更不一致。

第 1 版援引的审计测试（`audit view uses the actual server role instead of developer simulation`）不是同类逻辑：审计处用真实角色是为了决定**是否发起受保护 API 请求**（用模拟角色会漏取本可访问的数据，或拿到 403），而**导航与操作入口的可见性**仍由模拟角色控制。一个管网络请求，一个管界面呈现，判据不同。

补充两点，供将来复审时不必重开此题：

- 开发者在模拟视图下取消**自己**的预约不受影响 —— 条件里 `reservation.requesterUserId === currentUser?.id` 那一支与 `currentRole` 无关。
- 后端独立鉴权：`service.mjs:cancelReservation` 有 `actor?.role !== "developer" && reservation.requester_user_id !== actor?.id` → 403 `RESERVATION_CANCEL_FORBIDDEN`。前端这里纯属呈现，不涉及越权。

可选（1 行）：在 `currentRole` 声明处加一句注释，写明「模拟角色控制界面呈现，真实角色控制 API 请求判定」，避免下一轮复审再把它当 bug 提一遍。

## 6. 本批不做：前端启动全量加载（排入 v1.4.0）

`apps/web/app.js` 的 `loadApplicationData()` 目前全量拉取。后端 `listFilters` 已支持 `dateFrom` / `dateTo`，但**只在首次加载补两个参数会静默弄坏日历**：`displayedWeekStart` / `displayedMonth` 可以任意翻周翻月，而 `weekReservations()` / `monthReservations()` 只从内存已加载数据里过滤 —— 翻到窗口外会显示「暂无预约」，而不是报错。用户看到的是「数据没了」，比现在多加载几条更糟。

正确方案需要成套做：已覆盖区间的记录、增量合并、加载中状态、导航触发补拉。属于独立可测的功能，适合作为 v1.4.0 单独一项。

## 9. 2026-09-15 局域网部署补充（已执行）
